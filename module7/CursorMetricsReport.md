## Cursor Metrics Report – Orders API (Module 7)

### Cursor Contribution

- **Estimated Cursor contribution**: ~85%
  - Project scaffolding (`orders_api` package, `app.py`, models, schemas)
  - FastAPI endpoint implementations and pagination/filtering logic
  - Test suite structure and most test cases
  - README and this metrics report draft
- **Manual contribution**: ~15%
  - Validating architecture and trade-offs
  - Reviewing security considerations around filtering and SQLAlchemy usage
  - Adjusting comments, naming, and documentation for clarity

### Acceptance Rate

- **Suggestions shown vs. accepted** (conceptual estimate):
  - Code suggested or auto-completed by Cursor that was **accepted mostly as-is**: ~70%
  - Code that required **light edits** (naming, comments, minor refactors): ~20%
  - Suggestions that were **discarded or reworked**: ~10%

Cursor was especially helpful in quickly generating repetitive boilerplate
(Pydantic models, CRUD endpoints, and tests). Some suggestions for pagination and
filtering logic were refined to improve robustness and clarity.

### Estimated Time Saved

- **Without Cursor**: ~4–5 hours
  - Designing structure, wiring up FastAPI + SQLAlchemy
  - Hand-writing tests and coverage configuration
  - Writing README and metrics from scratch
- **With Cursor**: ~2 hours
  - Faster iteration on endpoint contracts and test cases
  - Rapid refactoring and navigation between files

**Estimated time saved**: ~2–3 hours (roughly 40–60%).

### What Was Generated vs. Manually Fixed

- **Generated by Cursor (primary)**:
  - `app.py` endpoint implementations, including:
    - `POST /orders`, `GET /orders`, `GET/PUT/DELETE /orders/{id}`
    - Pagination (`page`, `limit`) and filters (`status`, `min_amount`, `max_amount`,
      `start_date`, `end_date`)
  - `database.py`, `models.py`, `schemas.py`
  - `seed.py` script to populate 50 sample orders
  - `tests/test_orders_api.py` base structure and most test bodies
  - `module7/README.md` and this `CursorMetricsReport.md` initial text

- **Manually fixed or refined**:
  - Ensured Pydantic v2-compatible usage (`model_dump` instead of `dict`).
  - Cleaned up counting logic using `func.count` to avoid ORM pitfalls.
  - Reviewed filtering logic for security (parameter binding via SQLAlchemy).
  - Tightened parameter validation and comments for pagination and filtering.
  - Adjusted test imports and package layout so that `orders_api.tests` is a
    proper package (`__init__.py`) and tests can run reliably with pytest
    from the `module7` directory.

### Learnings: Where Cursor Helped vs. Struggled

- **Helped**:
  1. **Boilerplate-heavy setup**: Generating FastAPI app scaffolding, SQLAlchemy
     models, and Pydantic schemas was significantly faster with Cursor, reducing
     manual typing and configuration errors.
  2. **Test coverage scaffolding**: Cursor quickly produced a diverse set of tests
     (CRUD, pagination, filtering, edge cases) that could be iterated on instead of
     written from scratch.
  3. **Documentation drafts**: Creating a structured README and this report was
     accelerated by Cursor’s ability to turn requirements into organized markdown.

- **Struggled / needed manual oversight**:
  1. **Exact ORM patterns**: Initial counting and query snippets needed adjustments
     to use `func.count` properly and avoid accidental misuse of the SQLAlchemy API.
  2. **Framework version nuances**: Pydantic v1 vs v2 differences (e.g. `dict` vs
     `model_dump`) required manual correction to match the chosen version.
  3. **Package/test discovery details**: Pytest initially failed to import the
     `orders_api` package; fixing relative imports and adding `orders_api/tests/__init__.py`
     was done manually based on the concrete error messages.
  4. **Fine-grained API design decisions**: Decisions about page/limit validation,
     default values, and security-oriented comments (e.g. emphasizing parameter
     binding) benefited from manual judgment rather than relying solely on
     generated code.
